1 · Platform, scenario & topology

A scenario defines which components are installed; topology (below) defines how they're spread across machines. imaging-services is always required. Source: CAST's "choose your deployment" step at doc.castsoftware.com/imaging/install/global/docker.

Each analysis-node registers itself against the same imaging-services instance and can run on its own machine — this is CAST Imaging's horizontal scaling mechanism for analysis workload.

2 · Project scale

These bands are this tool's own planning heuristic, not an official CAST-published tier list — but the sizing figures they drive (results Section 1) are anchored to CAST's own documented example where one exists (up to 50 applications with 5 parallel analyses).

Only affects sizing when your scenario includes the Viewer or Dashboards (see the note in results Section 1's sizing) — headless/API-only scenarios aren't affected by concurrent browser traffic.

3 · Database

CAST Imaging supports PostgreSQL only as its RDBMS — no other engine is supported. Analysis and persistence data is stored here.

Neo4j is bundled with imaging-viewer (not user-selectable) — an ETL step loads analysis results from PostgreSQL into Neo4j for graph browsing in the Viewer. Only relevant when your scenario (question 1) includes the Viewer.

5 · Reverse proxy

A reverse proxy (or equivalent load balancer/Ingress/Gateway API) in front of Gateway is a mandatory prerequisite for installation, independent of whether HTTPS is enabled — CAST Imaging is not intended to be run with Gateway directly internet-facing. "Not decided yet" is a valid answer while planning, but must be resolved before install day.

6 · HTTPS / TLS certificate

HTTPS/SSL is not mandatory, but highly recommended — see question 5 for the mandatory reverse proxy it terminates on. "No HTTPS" is a valid choice for a fully trusted, isolated network segment, but is not recommended beyond that.
