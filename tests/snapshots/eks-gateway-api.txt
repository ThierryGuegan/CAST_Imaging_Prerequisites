Storage locations

On Kubernetes, storage is provisioned as persistent volumes/StorageClasses rather than host paths — block volumes (Amazon EBS) for the databases and logs, plus a shared-access (RWX) volume (Amazon EFS) that CAST's chart always requires. See CAST's cloud reference: storage-locations/cloud.

What CAST's Helm chart 3.6.9 itself creates (storage.yaml, values.yaml):

Always a shared pvc-shared-datadir (100 Gi by default), ReadWriteMany, on the FileClassName StorageClass — mounted by the console service and the control panel and the analysis-node (/opt/cast/shared: deploy, delivery, common-data). An RWX-capable file StorageClass is therefore always required, even with a single analysis-node pod (CAST's chart templates).
Block volumes (DiskClassName, ReadWriteOnce): castdir 100 Gi (/usr/share/CAST — extensions, logs), Neo4j data 100 Gi, ETL logs and CSV archive 10 Gi each, 1–2 Gi log volumes per service. The log/audit volumes are kept on uninstall (helm.sh/resource-policy: keep).
AWS EKS (K8SProvider: EKS): block volumes on EBS (ebs.csi.aws.com, gp3); pvc-shared-datadir on Amazon EFS (efs.csi.aws.com) — create the file system in the same VPC as the cluster, set EFSsystemID (and optionally EFSaccessPointID: access point castimaging-shared-datadir, root /castimaging-shared-datadir, owner UID/GID 10001, permissions 0755 — otherwise one is created at deployment), and create a mount target in every Availability Zone where worker nodes can run (a pod scheduled elsewhere times out mounting the volume). The mount targets must accept NFS, TCP 2049, from the cluster security group (eks-cluster-sg-<cluster>-<id>). Volumes can be increased but not reduced.

4. Reverse Proxy & HTTPS / TLS
A reverse proxy is a mandatory prerequisite. A reverse proxy (or equivalent load balancer/Ingress) in front of Gateway is required for installation, independent of whether HTTPS is enabled — CAST Imaging is not intended to be run with Gateway directly internet-facing.
HTTPS/SSL itself is not mandatory, but highly recommended — except with OpenID Connect (Section 5), where it is mandatory. CAST Imaging can be served over plain HTTP through that reverse proxy; enable HTTPS whenever the deployment is reachable beyond a fully trusted, isolated network segment — which in practice means almost every deployment beyond a fully offline POC. OpenID Connect is the other exception: CAST's OpenID Connect page lists access to CAST Imaging via HTTPS, already set up and configured, as a requirement before you register the client application.
Kubernetes networking (CAST's chart 3.6.9): exactly one of CreateLoadBalancer (default; exposes console-gateway-service as a cloud LoadBalancer), CreateIngress, UseIstioGateway or UseGatewayAPI (a GatewayClass controller such as NGINX Gateway Fabric). The Ingress template is nginx-specific (ingressClassName: nginx, nginx.ingress.kubernetes.io/* annotations) — install an ingress-nginx controller first; TLS comes from the Kubernetes secret tls-secret-cast (and tls-secret-cast-extend for the Extend proxy host) that you create in the CAST namespace (istio-system with Istio). The chart sets X-Forwarded-Host/-Proto/-Port from FrontEndHost, which matters when a reverse proxy or DMZ sits in front of the Ingress. Timeouts: NetworkTimeoutSeconds 300 s (Extend proxy 3600 s) — keep any outer proxy at least that high. Since 3.6.9 the gateway only forwards X-Forwarded-* headers when GATEWAYSERVICE.SPRING_CLOUD_GATEWAY_SERVER_WEBFLUX_TRUSTEDPROXIES is set (default ".*", a regex on the calling IP — restrict it to your ingress/Istio pod network if you wish); without it the OAuth2 login callback is built as http://, so any reverse proxy, load balancer or DMZ in front of the networking option must forward the original X-Forwarded-Proto/X-Forwarded-Host. With CreateIngress, CertManager.enable (off by default; issuer default vault-issuer, issuerKind, privateKeySize 4096) lets an already-installed cert-manager issue and renew tls-secret-cast.
Reverse proxy: Kubernetes Gateway API.
Certificate source: CA-issued.
You must provide the certificate and private key — CAST Imaging does not issue public TLS certificates.
Once HTTPS is confirmed working, disable the reverse proxy's own plain-HTTP listener (port 80) or keep only an HTTP→HTTPS redirect on it. Gateway's 8090 stays the proxy's internal upstream — keep it reachable only from the reverse proxy, not from users.
5. User authentication prerequisites

CAST Imaging authenticates users through an OpenID Connect-compliant identity provider (Microsoft Entra ID, Okta, Auth0…). The setup is done in parallel on two sides: at your identity provider, where CAST Imaging is registered as a client application, and in the Keycloak authentication system provided with CAST Imaging (realm aip-realm), where the provider is declared and its claims are mapped onto CAST Imaging groups. The Keycloak side is identical whichever provider you use. Source: CAST's Authentication – OpenID Connect page (install/authentication).

Prerequisites
Access to CAST Imaging via HTTPS already set up and configured (Section 4).
Administrator access to your identity provider (to register a client application) and to Keycloak, using the kcadmin account.
The clock of the cluster nodes running imaging-services must be accurate and synchronized (NTP): token validation is time sensitive, and the token exchange between Keycloak and your provider is a direct server-to-server call, not a browser redirect.
Network: the SSO Service pod must reach the provider's discovery, token, UserInfo and JWKS endpoints server to server (see Section 3); a failure to retrieve the discovery document or signing keys usually means a firewall or proxy, not wrong URLs.
Configuration steps
Alias and redirect URI. Choose a short, lowercase, hyphenated alias (e.g. my-idp, no spaces or special characters); it forms the redirect URI your provider needs: https://<imaging-fqdn>/auth/realms/aip-realm/broker/<idp-alias>/endpoint.
Register CAST Imaging at your provider as a confidential / web application (not public or single-page), entering the redirect URI character for character, and generate a client secret (often shown only once). Collect the Client ID, the Client secret and the discovery endpoint (.well-known/openid-configuration) — or, where none is published, the authorization, token, UserInfo and JWKS URLs.
Claims. CAST Imaging requires email, given_name and family_name (emitted by most providers once the profile and email scopes are enabled; Keycloak imports them automatically — no mapper needed, unlike SAML). For group-based permissions (recommended) your provider must also emit a role/group claim (e.g. roles, groups, memberOf): confirm its exact name, the values it carries and any extra scope it needs.
Declare the provider in Keycloak (aip-realm → Identity providers → OpenID Connect v1.0): alias, discovery endpoint, Client ID and secret, a client authentication method (Client secret sent as post is the most widely supported and the default when your provider's docs say nothing; also basic, JWT with the secret, or JWT with a private key), and scopes openid email profile plus any scope the role/group claim needs. Optionally enable Trust Email and set Allowed clock skew to a few seconds. Then check that the Redirect URI Keycloak shows is identical to the one registered.
Groups and mappers. Group import is not supported: create each group in Keycloak (its name = the exact claim value) and add a Claim to Group mapper per group (sync mode Force recommended; use Regex Attribute Values such as ^architect$ when the claim is an array). Don't add mappers for email, given_name or family_name.
Permissions. By default OIDC users have none: grant the ADMIN profile to at least one OIDC user — CAST recommends doing it with local authentication (admin / admin) and User Permissions — then assign profiles to the synchronized groups in CAST Imaging (User permissions → Users → Refresh).
Test the login in a private browsing window. A prompt for first/last name means the standard claims aren't arriving.
Disable the existing authentication methods. CAST highly recommends disabling or deleting the Local Authentication users/groups (temporarily switch OIDC off so they become visible, then re-enable it) so nobody can use a back-door login.

Troubleshooting (per CAST): if the provider isn't offered at login, set the realm's Login theme to keycloak; decode the ID token (browser DevTools → Network → Preserve log) to check the claims; invalid/expired-token errors are often clock drift; the user is authenticated but in no group when the mapper's claim name or value (case included) doesn't match the token.

6. CAST Extend access & licensing
Allow outbound HTTPS (443) from imaging-services and every analysis-node to extend.castsoftware.com.
Generate an API key from the CAST Extend website and configure it in CAST Imaging / CAST Extend client to authenticate extension downloads.

7. MCP Servers (AI features) — enabled
Deploy the CAST Imaging MCP Server 3.1: one container (castimaging/imaging-mcp-server:3.1.0 — CAST's installer rejects the latest tag) runs the MCP Aggregator Gateway on :8285 with the Structural (8282), Semantic search (8287) and Text2Cypher (8289) MCP servers behind it on its loopback; it needs CAST Imaging 3.6.9 or later (the chart README says 3.6.8) and Viewer.enable: true and is reached through Gateway on the /mcp path — clients never connect to :8285 directly. Per CAST's MCP 3.1 Docker page and the Helm chart.
Database access: the MCP servers do not connect to PostgreSQL (not stated on CAST's MCP pages). The Semantic search and Text2Cypher servers connect to Neo4j (Bolt 7687, part of your Viewer scenario).
Gatekeeper MCP (castimaging/gatekeeper-mcp-server, TCP 8283, path /mcp/gatekeeper) is a standalone container installed alongside the MCP Server: it connects AI clients to the CAST Dashboard REST API (/dashboards/rest on imaging-services; API-key sign-in needs CAST Imaging 3.6.6 or later, the component itself 3.6.4 or later). Its telemetry push to CAST is on by default (TELEMETRY_PUSH_ENABLED, every 120 minutes; the host isn't stated) — set it to false on networks without outbound access. On Kubernetes: CAST's Helm chart 3.6.9 deploys only mcp-server (McpServer.enable: true, requires Viewer.enable: true; health check /mcp/healthcheck) — it has no Gatekeeper template or image, so confirm with CAST how Gatekeeper is deployed there.
Client authentication (CAST's MCP security page): an API key sent in the x-api-key header (still supported), or an OAuth browser sign-in for Claude Code and VS Code — one or the other per client. The identity provider is CAST Imaging's own Keycloak (realm aip-realm, kcadmin), not an external one: the page mentions no external OAuth2/OIDC provider. OAuth needs CAST Imaging 3.6.6 or later, MCP Server 3.0.4 or later and Gatekeeper 3.0.1 or later. In Keycloak (Realm settings → Client policies) create, per AI client, a profile with the client-id-metadata-document executor and a policy, and link the profile to the policy (CAST calls a missing link the most common mistake): Claude Code — cimd-profile-claude / cimd-policy-claude, trusted domains claude.ai, localhost, 127.0.0.1; VS Code — cimd-profile-vscode / cimd-policy-vscode, trusted domains vscode.dev, code.visualstudio.com, 127.0.0.1. Clients reach only the Gateway (/mcp, /mcp/gatekeeper, and /.well-known/oauth-protected-resource/mcp, which CAST Imaging redirects to Keycloak's discovery endpoint) — never expose the MCP Server or Keycloak directly. HTTPS is highly recommended; plain HTTP is acceptable only on a trusted local or CI host not reachable from the internet. Check: an unauthenticated POST to /mcp must answer with a WWW-Authenticate: Bearer resource_metadata=… header.
LLM provider selected: Anthropic API — allowlist exact FQDN api.anthropic.com on the MCP client hosts, not the CAST Imaging servers (no wildcards).
Licensing and settings (CAST's MCP 3.1 pages): from CAST Imaging 3.6.9 the Semantic search MCP needs a license key that includes GraphRAG (otherwise it reports "Not licensed"); IMAGING_CODE is false by default, so source code is not returned to the AI client; a private or self-signed CA needs SSL_CA_BUNDLE (Base-64 PEM, root and intermediate combined); with domain mapping clients still send x-user-tenant; CAST says the MCP Server and Keycloak must never be exposed directly and HTTPS on the CAST Imaging gateway is highly recommended.
Sizing: CAST's MCP pages give only at least 2 GB of free disk (CPU and RAM: the general hardware requirements) and don't say whether the MCP servers can share a machine with other CAST Imaging components; the MCP servers have their own installers. The ~2 vCPU / 4 GB RAM / 20 GB disk added to the core row in Section 1 (Imaging MCP + Gatekeeper MCP combined) is this tool's estimate, not a CAST figure — split it out yourself if you need per-container limits.
