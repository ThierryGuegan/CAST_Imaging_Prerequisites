Storage locations

On Kubernetes, storage is provisioned as persistent volumes/StorageClasses rather than host paths — block volumes (Azure Disks) for the databases and logs, plus a shared-access (RWX) volume (Azure Files) that CAST's chart always requires. See CAST's cloud reference: storage-locations/cloud.

What CAST's Helm chart 3.6.9 itself creates (storage.yaml, values.yaml):

Always a shared pvc-shared-datadir (100 Gi by default), ReadWriteMany, on the FileClassName StorageClass — mounted by the console service and the control panel and the analysis-node (/opt/cast/shared: deploy, delivery, common-data). An RWX-capable file StorageClass is therefore always required, even with a single analysis-node pod (CAST's chart templates).
Block volumes (DiskClassName, ReadWriteOnce): db-data 128 Gi (embedded PostgreSQL), castdir 100 Gi (/usr/share/CAST — extensions, logs), 1–2 Gi log volumes per service. The log/audit volumes are kept on uninstall (helm.sh/resource-policy: keep).

4. Reverse Proxy & HTTPS / TLS
A reverse proxy is a mandatory prerequisite. A reverse proxy (or equivalent load balancer/Ingress) in front of Gateway is required for installation, independent of whether HTTPS is enabled — CAST Imaging is not intended to be run with Gateway directly internet-facing.
HTTPS/SSL itself is not mandatory, but highly recommended — except with SAML SSO (Section 5), where it is mandatory. CAST Imaging can be served over plain HTTP through that reverse proxy; enable HTTPS whenever the deployment is reachable beyond a fully trusted, isolated network segment — which in practice means almost every deployment beyond a fully offline POC. SAML SSO is an exception: browsers and IdPs require an HTTPS redirect/callback URL, so HTTPS is a hard requirement whenever SAML is selected (CAST's HTTPS/SSL page states that an HTTPS connection is a prerequisite for configuring SAML authentication).
Kubernetes networking (CAST's chart 3.6.9): exactly one of CreateIngress, UseIstioGateway, UseGatewayAPI (a GatewayClass controller such as NGINX Gateway Fabric) or UseApplicationGateway (Azure Application Gateway, created separately) can be enabled — the installation fails otherwise. CreateLoadBalancer (default true) is not part of that check: left on, it exposes console-gateway-service as a cloud LoadBalancer in addition to the option you chose (CAST support), so set it to false when only that option should expose CAST Imaging. The Ingress template is nginx-specific (ingressClassName: nginx, nginx.ingress.kubernetes.io/* annotations) — install an ingress-nginx controller first; TLS comes from the Kubernetes secret tls-secret-cast (and tls-secret-cast-extend for the Extend proxy host) that you create in the CAST namespace (istio-system with Istio). The chart sets X-Forwarded-Host/-Proto/-Port from FrontEndHost, which matters when a reverse proxy or DMZ sits in front of the Ingress. Timeouts: NetworkTimeoutSeconds 300 s (Extend proxy 3600 s) — keep any outer proxy at least that high. Since 3.6.9 the gateway only forwards X-Forwarded-* headers when GATEWAYSERVICE.SPRING_CLOUD_GATEWAY_SERVER_WEBFLUX_TRUSTEDPROXIES is set (default ".*", a regex on the calling IP — restrict it to your ingress/Istio pod network if you wish); without it the OAuth2 login callback is built as http://, so any reverse proxy, load balancer or DMZ in front of the networking option must forward the original X-Forwarded-Proto/X-Forwarded-Host. With CreateIngress, CertManager.enable (off by default; issuer default vault-issuer, issuerKind, privateKeySize 4096) lets an already-installed cert-manager issue and renew tls-secret-cast.
Azure Application Gateway (CAST's AKS page and its Azure-ApplicationGateway-for-CastImaging.pdf, chart repository): set UseApplicationGateway: true. Prerequisites in the PDF: a valid PFX certificate with its passphrase, the Azure permissions to create Application Gateways, and the permission to create the DNS record that points the FQDN at the gateway's listener IP. Procedure: a subnet dedicated to Application Gateways, IPv4 only (IPv6 is not supported by Imaging), a public frontend IP; a backend pool holding the external IP of console-gateway-service; an HTTPS listener on port 443 with the PFX uploaded (the portal also offers a Key Vault certificate — the PDF uses the upload; with a shared gateway use a multi-site listener with the FQDN as host name); a backend setting HTTP, port 8090, cookie affinity and connection draining off, request time-out left at 20 s in the screenshot, no host-name override, no custom probe; then the FQDN's DNS record on the gateway's public IP. Check Backend health: the backend must be Healthy, answering 302. A rewrite rule set is needed for SAML SSO: request headers X-Forwarded-Host = your public FQDN, X-Forwarded-Proto, X-Scheme and X-Forwarded-Scheme = https, and X-Real-IP / X-Forwarded-For deleted; before Imaging 3.6.4 also a cookie-rewrite response rule adding SameSite=None; Secure to Set-Cookie (not needed from 3.6.4 — remove it). CreateLoadBalancer with Application Gateway — to confirm with CAST: CAST support says CreateLoadBalancer is outside the single-option check (leaving it on does not fail the installation, but adds a separate load balancer next to your option) and the values reference says it should be false, yet the PDF takes the backend from the console-gateway-service external IP (a LoadBalancer Service in its screenshot) — whether to keep it on for the backend, and whether that load balancer should be internal, is not stated. Reasonable inference, not in the PDF: the 20 s request time-out is below the chart's NetworkTimeoutSeconds (300 s) and Extend proxy 3600 s, so raise it if long requests fail.

5. User authentication prerequisites
HTTPS must already be set up on CAST Imaging (CAST's SAML page; Section 4) — plain HTTP is not a valid choice with SAML.
Export CAST Imaging's own SAML metadata from Keycloak (aip-realm → Realm settings → General → SAML 2.0 Identity Provider Metadata, saved as metadata.xml) and send it to your identity team, who register CAST Imaging as a Service Provider and return an IdP metadata URL.
Declare the IdP in Keycloak (aip-realm → Identity providers → SAML v2.0): the metadata URL goes in SAML entity descriptor and the settings fill in by themselves.
Attribute mappers firstName, lastName and email (type Attribute Importer; Attribute Name = the ClaimType URI found in the IdP metadata; name format ATTRIBUTE_FORMAT_BASIC).
Groups (optional): the IdP must send them in the assertion and group import is not supported — create each group in Keycloak and add an Advanced Attribute to Group mapper per group (key = the group attribute name, value = a regex, Regex Attribute Values on, sync mode Force); the attribute name is read by decoding the SAMLResponse in the browser's DevTools.
Grant the ADMIN profile to at least one SAML user with the local admin account and test the login; CAST then recommends disabling the existing authentication methods (switch SAML off temporarily to see the local users). Keep a documented break-glass procedure for an IdP outage (this tool's recommendation). If SAML is not offered at login, set the realm's Login theme to keycloak.
Network: browser ⇄ IdP over HTTPS (443) and CAST Imaging fetching the IdP metadata (see Section 3) (reasonable inference from the SAML flow — CAST's page names no port).

Source: CAST's Authentication – SAML page (install/authentication/saml).
