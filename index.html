CAST Imaging Documentation / Overview

1. Purpose & Scope

Architecture and installation prerequisites for CAST Imaging and its associated modules (Console, Viewer, MCP Servers, Extend integration).

This document consolidates the architecture and installation prerequisites for CAST Imaging, based on the structure of the official CAST documentation portal (doc.castsoftware.com/imaging/install). It is intended for Solutions Architects, Infrastructure/DevOps teams, and Security/Network teams who need to plan, size, and prepare an environment prior to installing CAST Imaging.

Validation notice. This document was compiled from CAST Imaging's published installation documentation structure and standard CAST Software deployment practices. Exact version numbers, minimum supported OS/DB versions, and default ports evolve with each CAST Imaging release. Always cross-check the figures in this document against the current version of doc.castsoftware.com/imaging/install for the specific CAST Imaging release you are deploying before finalizing infrastructure orders, firewall change requests, or security sign-off.

How to use this document

  • Section 2 helps you choose a platform, deployment scenario, and topology.
  • Section 3 gives sizing tables refined by the choice made in Section 2.
  • Sections 4–5 cover the MCP (AI) servers and the installation procedures per platform.
  • Sections 6–11 cover everything Security/Network teams need: HTTPS, authentication, CAST Extend access, outbound flows, exact port matrix, and licensing.
  • Section 12 is a consolidated, printable checklist.
  • Machine-readable exports: network-and-ports-matrix.csv and sizing-requirements-matrix.csv.

2.1 Choosing a Platform

Supported host platforms for CAST Imaging
PlatformDescriptionBest fit for

2.2 Choosing a Scenario

Evaluation / POC

Fastest setup, minimal hardening, single machine, self-signed certs acceptable, local authentication.

Standard Production

Hardened OS, HTTPS with CA-signed certificate, SSO (SAML/LDAP), backups, monitoring, dedicated DB.

Enterprise / High Availability

Multi-machine or Kubernetes, redundancy at web/app tier, managed/clustered database, centralized log/metric collection, change-managed upgrades.

2.3 Choosing a Topology (Single vs. Multi-Machine)

Topology decision matrix by situation
SituationRecommended TopologyRecommended PlatformRationale
Proof of Concept / trial, <~50 applicationsSingle machine (all-in-one)Docker / PodmanMinimizes setup effort; all services (web, application, database) co-located on one host or one docker-compose stack.
Small team, 1 project, <~150 applicationsSingle machine, or multi-machine with a dedicated DB hostDocker / Podman / WindowsSingle machine is usually sufficient; separate the database early if growth is expected.
Multiple teams / departments, shared platformMulti-machine (dedicated web/app node + dedicated DB node)Docker / Podman / KubernetesIsolates DB I/O from web/app workload; simplifies backup and scaling of the database independently.
Enterprise-wide rollout, HA / SLA requirementsMulti-machine, redundant web/app tierKubernetes (preferred) or clustered Docker/Podman hosts behind a load balancerEnables rolling upgrades, horizontal scaling, and failover without downtime.
Regulated / air-gapped environmentSingle or multi-machine, offline install bundlePodman (rootless) or WindowsAvoids Docker daemon root requirement; supports offline/registry-mirrored image delivery.
Rule of thumb. Start single-machine for POCs and small teams; move the database to its own host (or managed service) as soon as the deployment becomes production-facing or exceeds ~150 delivered applications, or when multiple concurrent users/CI pipelines push load onto the database.

General hardware guidance

  • SSD (or equivalent low-latency block storage) is strongly recommended for the database tier in all scenarios.
  • CPU should favor higher single-core performance for the analysis/indexing engine; RAM sizing should account for concurrent analyses.
  • Reserve headroom (20–30%) above the minimum for OS, container runtime, and monitoring agents.
  • Virtualized hardware (VMware/Hyper-V/cloud VM) is fully supported; avoid CPU/RAM oversubscription on the database host.

4. MCP Servers Overview

Reference: imaging/mcp-server/, mcp-server/imaging/, mcp-server/gatekeeper/, mcp-server/oauth/

CAST Imaging exposes its knowledge base to AI assistants and coding agents via the Model Context Protocol (MCP). This introduces additional components and network flows beyond the core web/application/database stack.

CAST Imaging MCP Server

Exposes CAST Imaging's application knowledge (architecture, dependencies, transactions) as MCP tools/resources so AI assistants (e.g. IDE copilots, chat agents) can query it in natural language.

Gatekeeper

Acts as an authorization/policy front-door in front of the MCP server(s), enforcing which clients/users can call which MCP tools and against which applications.

OAuth Module

Provides OAuth2 / OIDC-based authentication for MCP clients, so AI assistants authenticate as the requesting user rather than with a shared static secret.

Prerequisites specific to MCP Servers

  • A running, reachable CAST Imaging instance (the MCP server is a companion service, not a replacement for the core platform).
  • An OAuth2/OIDC provider (built-in, or the same IdP used for SAML/LDAP SSO) reachable from both the MCP Gatekeeper and the end-user's AI client.
  • Outbound HTTPS (443) from the MCP server host to the configured LLM API endpoint, if AI-generated natural-language responses are used (see Section 9).
  • Inbound connectivity from AI client tooling (IDE plugin, chat client, orchestration agent) to the MCP server/Gatekeeper endpoint — typically HTTPS 443, proxied the same way as the main Imaging web UI.
  • Sizing: lightweight relative to the core platform — see sizing-requirements-matrix.csv (2 vCPU / 4 GB RAM indicative per MCP service).
Security note. Because MCP tools can expose detailed architecture, data-flow, and dependency information (and, via Gatekeeper, potentially broader actions), always front the MCP endpoint with the OAuth module and Gatekeeper policy enforcement in any environment beyond an isolated POC, and restrict outbound LLM traffic to the exact FQDNs required by the chosen AI provider (see Section 9).

6. HTTPS / SSL

Reference: install/https-ssl/

Customer responsibility. CAST Imaging does not issue public TLS certificates. The customer must provide a valid certificate (from an internal or public Certificate Authority) and terminate/configure TLS, typically via a reverse proxy placed in front of CAST Imaging.

Prerequisites

  • A certificate + private key (PEM/PFX) issued for the fully-qualified domain name (FQDN) under which CAST Imaging will be published.
  • A reverse proxy or load balancer capable of TLS termination — e.g. Nginx, Apache HTTPD, HAProxy, F5, IIS with ARR, or a Kubernetes Ingress controller — sitting in front of the CAST Imaging web front end.
  • Decision on TLS termination point: at the reverse proxy (recommended, offloads TLS from the application containers) vs. pass-through to the CAST Imaging web container itself.
  • Certificate renewal process defined (manual or automated, e.g. via an internal PKI or ACME/Let's Encrypt where externally facing).
  • HTTP → HTTPS redirect configured; disable plain HTTP once HTTPS is validated.

Typical topologies

  1. Reverse proxy in front of a single-machine Docker/Podman deployment — proxy terminates TLS, forwards to the internal web service port over HTTP on a private network segment.
  2. Kubernetes Ingress — Ingress controller (e.g. NGINX Ingress, Traefik) holds the TLS secret and routes to the CAST Imaging Service.
  3. Native Windows install — IIS or a dedicated reverse proxy in front of the CAST Imaging web service.

8. CAST Extend Access

CAST Imaging relies on CAST Extend (extend.castsoftware.com) to download extensions/technology packages, product updates, and (depending on licensing model) license-related artifacts.

  • Outbound HTTPS (443) from the CAST Imaging server to extend.castsoftware.com must be allowed (see Section 9 for the exact FQDN entry).
  • An API Key must be generated from the CAST Extend website and configured in CAST Imaging (or the CAST Extend Local Update Server, if used) to authenticate extension downloads.
  • For air-gapped/regulated environments without direct internet access, use a CAST Extend Local Update Server (offline mirror) deployed inside the network, which itself needs outbound access to extend.castsoftware.com and is the only component required to reach the internet.
  • Proxy support: if outbound traffic must transit an authenticated HTTP(S) proxy, configure the proxy settings in CAST Imaging / CAST Extend client accordingly before first extension download.
Optional CAST Extend Local Update Server. Consider this component whenever individual CAST Imaging nodes must not have direct internet egress — it centralizes and audits all extension/update downloads through a single controlled outbound path.

11. Licensing

  • A valid CAST Imaging license file must be obtained from CAST Software (via your CAST account team or CAST Extend) and supplied during installation/configuration.
  • The license governs entitlement scope — e.g. number of applications, users, or modules (including whether MCP/AI features and Highlight integration are enabled).
  • Plan the license renewal date into operational calendars; expired licenses can block analysis delivery or console access depending on grace-period configuration.
  • An API key generated from the CAST Extend website is required separately from the license file, to authenticate automated extension/update downloads (see Section 8).
  • Keep both the license file and API key in a secure secrets store (e.g. Kubernetes Secret, vault, encrypted file) rather than embedded in plain configuration files under version control.
Two distinct credentials. Do not confuse the license file (product entitlement) with the CAST Extend API key (download authentication) — both are required, obtained separately, and must be renewed/rotated independently.

12. Pre-Installation Checklist

Consolidated, printable checklist derived from Sections 2–11.

Architecture

  • Platform selected (Windows / Docker / Podman / Kubernetes)
  • Scenario selected (POC / Standard Production / Enterprise-HA)
  • Topology selected (single-machine vs. multi-machine) and documented

Infrastructure

  • Server(s) provisioned meeting CPU/RAM/disk sizing for the chosen scenario
  • Database engine selected, sized, and provisioned (dedicated instance recommended)
  • Persistent storage locations identified and separated (DB / logs / workspace / backup)
  • DNS name(s) reserved and resolvable
  • NTP time synchronization configured

Security & Network

  • TLS certificate obtained; reverse proxy / Ingress selected and configured
  • Authentication method decided (Local / SAML / LDAP) and IdP/LDAP prerequisites gathered
  • All inbound/outbound firewall rules from the Network Ports Matrix opened
  • Exact FQDNs allowlisted (no wildcards) for extend.castsoftware.com and any optional integrations
  • Outbound proxy configuration (if applicable) validated for CAST Extend access

MCP Servers (if AI features enabled)

  • MCP Server and Gatekeeper deployment planned alongside core platform
  • OAuth2/OIDC provider identified for MCP client authentication
  • LLM provider selected and its exact API FQDN allowlisted

Licensing & Access

  • CAST Imaging license file obtained and ready to install
  • CAST Extend API key generated and stored securely

End Users

  • End-user workstation requirements communicated (browser, RAM, resolution)
  • Delivery/analyst workstation requirements communicated (JRE, SCM clients, workspace disk)
